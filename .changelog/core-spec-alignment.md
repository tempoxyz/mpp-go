github.com/tempoxyz/mpp-go: minor
---

Aligned servers and clients with the core and Tempo charge specifications: replays now get 402 invalid-challenge with a fresh Challenge, Challenges carry a 16-byte `_mpp_nonce` (`_mppx_nonce` still verifies), credentials are checked in the specified order with multiple credentials rejected as 400 and unselected or bare ones ignored, and `VerifyOrChallenge` refuses secrets under 32 bytes. Tempo servers enforce a new `methodDetails.memo` (`ChargeParams.Memo`) on the primary transfer, and routes that set it accept only pull (transaction) payments: push is dropped from their `supportedModes`, hash credentials are refused, and `Memo` with push-only `SupportedModes` is a configuration error. Push (hash) payments must still carry the Challenge's attribution memo, while pull payments may carry it, another memo or none, but never an attribution memo for another realm or Challenge. An `OnChallenge` hook returning `client.ErrPaymentDeclined` before the method runs now returns the 402 without paying. The HTTP and MCP clients no longer pay a fresh Challenge that answers a sent Credential with invalid-challenge: the MCP client returns a `ReconciliationError` holding the sent Credential. Tempo servers now reject a pull (transaction) credential whose transaction is already on chain before their own broadcast with verification-failed, as mppx does, instead of settling it from its receipt, unless the server broadcast that transaction itself for the same Challenge: it records each broadcast in the replay Store first, so a retry after an unknown outcome, a receipt timeout or a failed replay store write settles the landed transaction once.
