Tempo charge settlement no longer locks out a paid credential. When the receipt wait fails after a successful broadcast, the verifier releases its replay claims and returns a verification error saying the outcome is unknown; a retry with the same credential first looks up the receipt of the transaction it would broadcast and, when that transaction is already included, settles from its receipt without simulating it again (its spent balance and nonce would fail the simulation); otherwise it re-broadcasts the signed transaction, which the node includes at most once, as in mppx. A local fee payer re-signs a sponsored retry identically, so sponsored retries recover the same way; with a local fee payer, the sponsored sender is now simulated after its replay claim and co-signature. The receipt wait now outlives a client disconnect within its existing budget, sponsored charges release their claim the same way, and claims are kept only for a transaction that was included (reverted, or not satisfying the charge), including a reverted transaction found after `eth_sendRawTransaction` fails, which now returns `transaction reverted` instead of `transaction submission failed`. The verifier rejects a broadcast hash that differs from the signed transaction's hash, and a failure to release a claim after a failed broadcast is now reported instead of ignored.

Add the optional `tempo.ExpiringStore` interface (`PutIfAbsentUntil`), implemented by `MemoryStore` and `RedisStore`, and the opt-in `ExpireReplayKeys` setting on the charge server's `Config` and `IntentConfig`. With it, the verifier lets replay keys expire ten minutes after the challenge's expiry, the moment after which the credential can no longer be accepted; it requires a store that implements `tempo.ExpiringStore`, and is only safe when credentials reach the verifier through `server.Mpp`, which verifies the challenge HMAC including its expiry. By default replay keys are still kept forever with `PutIfAbsent`. `RedisStore.Get` matches `redis.Nil` with `errors.Is`.
